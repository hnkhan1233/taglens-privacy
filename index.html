TagLens — Privacy Policy

Last updated: 24 September 2026

TagLens is a developer diagnostic tool. It records the analytics activity of a web page you are visiting so you can see what your tracking did and did not send. This policy describes exactly what it handles and where that data goes.

The short version

TagLens does not have a server. Nothing it records is transmitted anywhere by default. There is no account, no login, no telemetry, no analytics on the extension itself, and no third party receives any of it. Everything the extension captures stays in your own browser's storage on your own machine.

One exception is a feature you switch on yourself: AI analysis, which lets you put questions about a recording to an AI model using your own API key. When you use it, TagLens sends that model a fact sheet about the recording — event names, how many times each fired, whether each reached Google Analytics, the findings on the report, and the values the site put in its data layer — page types, placements, search terms, product names and the like. It does not send a person's identifiers: parameters that identify someone — email, phone, user, account, session and device ids, addresses, and anything shaped like one — are listed by name only, and their values never leave your machine. Nothing is sent until you type a question, and nothing at all is sent if you never connect a key. The key is stored in your browser's local storage and is shown back to you only as its last four characters.

Optional page checks (version 1.2.0)

The page reader is off by default. You enable it separately for each website, and it reads only while that tab is recording. It reads short text, headings, image descriptions, selected HTML attributes and nearby element IDs, links, and visibility measurements from candidate page blocks. It does not take screenshots or read form values, editable areas, or deliberately hidden text. Page and resource addresses omit query strings and fragments. Up to 100 observations are stored with a recording; they follow the same save/delete rules and can appear in JSON and report exports. Site opt-ins and tracking rules are stored locally until you remove them.

Tracking suggestions are computed locally from the recording. If you press Preview image, TagLens requests that recorded image address from its host, without cookies or a referrer, and displays the response locally. The host sees the image request and your IP address. Previews are limited to 2 MB, are not saved in the recording, and may show a newer image than the one originally seen. No image is sent to Jev. Show on website scrolls to and briefly outlines the recorded block if it is still present.

Jev classification is a separate, explicit action. If you supply a TypeSafe API key, select a block, approve sending its text, and press Ask Jev, TagLens sends that block to https://api.typesafe.ai/v1/systemone. The request contains short titles and text, link labels, image descriptions, and HTML attribute names. It excludes page addresses, link/image URLs, selector strings, attribute values, recordings, and analytics events. Recognizable emails, phone numbers, and common credential patterns are masked. This is not a guarantee that all personal information has been removed: other names or personal details may remain. The screen shows a preview before sending. TypeSafe's data terms apply to the material you send. The key is held in Chrome local storage, is never returned to the screen, and is excluded from exports. Remove it using the Page checks screen. Saving a key or enabling page reading does not send a request to Jev.

What runs on every page

TagLens is a diagnostic tool, so a small amount of it has to be in place before you decide to record — otherwise pressing record would always miss the beginning of the page, which is the part being diagnosed. On every page you open, in every frame, whether or not you are recording, TagLens:

  • Watches dataLayer in the page so that a push made in the first milliseconds of a page load is not lost.
  • Sets one attribute, data-tag-assistant-prod-present, on the page's root element. This switches on a reporting channel that Google's own tag already carries and that Google's Tag Assistant uses. It makes the tag write down, in the page, each event it sends, which is what lets TagLens tell apart events that leave together in a single batched request. The attribute has to be in place before Google's tag starts, and Google's tag reads it exactly once, so it cannot be switched on only when you press record.
    • It does not change what the site sends. This was measured across 138 runs against Google's own tag: the requests, their parameters, their values, the cookies and the headers are identical with the attribute and without it.
    • What it does do is leave a record of that page's recent Google hits inside the page itself, where other scripts on that same site could read it. If you would rather that did not happen on a particular site, do not open that site with TagLens installed.
  • Asks the extension whether this tab is being recorded. Chrome attaches the page's address to that question as sender information. The optional page reader uses its origin to check the site's opt-in setting, and the browser makes it available, so the extension is capable of knowing the address of pages you open. The page's origin — the site name, not the full address — is also held in session memory for the tab, and is gone when the browser closes. Separately, whenever you open TagLens on a tab it writes that tab's site name to its own settings storage, which is on disk, so that a screen opened in a new tab can find its way back to the live timeline. It is overwritten the next time you open TagLens and it never leaves your machine.

One thing happens outside the page, and it is worth stating plainly. Chrome hands an extension that is allowed to read requests a copy of every analytics request any tab sends, headers included, before that extension gets to decide whether it wants it. TagLens looks at each one to see whether it is a tracking request at all, and on a tab you are not recording it is dropped without being stored, shown or counted. There is no way to ask Chrome for one tab's requests only; the choosing has to happen after they arrive.

Apart from that, nothing about the page or about you leaves a tab you have not recorded. Two things are worth stating precisely, because "not recording" is not quite the same as "never recorded":

  • Recording is armed per page. A page you were recording keeps sending until you leave it, even after you press stop — the extension throws that away, and nothing from it is saved. It works this way because TagLens numbers the records it reads out of Google's tag, one run of numbers per page, and a gap in that numbering makes it distrust the whole page's evidence. A page that could stop reporting half way through would punch that gap itself.
  • A new page opened after you stop sends nothing at all.

What TagLens records

While you are recording, and only on the tab you are recording, TagLens captures:

  • dataLayer pushes made by the page, including their contents. When recording starts, up to the last 300 entries already sitting in the page's dataLayer are read as well, marked as having happened before recording began, because they are the part of the page load you pressed record to see.
  • Analytics requests the page sends — the URL, the decoded payload (event name and parameters), and a summary of the request headers. The summary counts sizes and lists the names of the largest cookies sent with the request. It never keeps a cookie's value.
  • The page's address, so that captured events can be attributed to the page that produced them. TagLens does not read the page's title; a title appears in a recording only if the site's own analytics put it in a request.
  • Clicks and form submissions, so that a control that fired nothing can be told apart from one nobody pressed. What is kept is what Google Tag Manager's own click variables would see: the visible text of the control up to 60 characters, its tag, its id, its classes, its link address, and a selector for it. Typing is never recorded, and neither is the content of a form.
  • Whether the site's consent banner says you have decided, and whether it reports consent for storing information on your device. This comes from the site's own consent API and explains a recording that is empty because nothing was allowed to fire. It is three true-or-false values, kept with the recording; no identifier from the banner is stored.
  • Your own settings and saved comparisons.

Because analytics payloads are the subject of the tool, a recording will contain whatever the site under test chose to put into them. On some sites that can include identifiers such as a user or account ID. TagLens surfaces this to you — that is frequently the defect being looked for — but it does not extract, separate, or transmit it.

Where it is stored

Recordings are kept in a database called taglens in your browser's own IndexedDB storage. Your settings, saved journeys and comparisons are kept in chrome.storage.local, and the recording in progress is mirrored into chrome.storage.session so that Chrome shutting the extension down mid-session cannot lose it. All three are areas of your own browser profile on your own device. The unlimitedStorage permission is requested so that a long recording is not silently truncated.

A recorded session is a draft until you press save this session. A draft is written to disk as it goes — so that closing your browser or Chrome suspending the extension cannot lose it mid-session — but it is not kept. It is discarded when you close the last TagLens view, once the recording it came from has finished. A draft whose tab you still have open is not thrown away underneath you; it waits, and goes the next time you close TagLens after that tab is gone.

A session you save with that button is kept until you delete it or remove the extension. Recordings made before saving existed are kept for 30 days. Recordings a saved journey was cut from, and journeys used as a comparison baseline, are kept for as long as the thing that refers to them. A recording made by replaying a journey is shown as saved, because you asked for the run; it is kept while the journey still refers to it, and otherwise ages out with the rest. Once there are more than a hundred recordings the oldest go first, counting only the ones you did not save yourself — what you saved is not deleted to make room.

Uninstalling the extension removes them with it. TagLens has no ability to recover a recording once deleted, because it never held a copy.

Network activity

TagLens fetches public tracking definitions and supports two optional AI requests. AI requests happen only after you connect a key and explicitly ask for analysis or classification.

While you are recording, when it detects that the page has loaded a Google Tag Manager container, it performs a single GET for that container's public definition in order to determine which tags should have fired. Where TagLens saw the page request the container, it fetches that same URL — the identical URL the page itself has already requested, on whichever host the page loaded it from: usually googletagmanager.com or the site's own server-side Tag Manager domain. Where the page holds a container TagLens never saw requested (a container loaded through a first-party loader path), it fetches the container's public definition from the URL the page's own script tag names, or failing that from googletagmanager.com by the container's public id. No data is sent with that request and no cookies or credentials are attached to it. On a tab you are not recording, this request is not made at all.

The second is the AI analysis feature. With a key you have connected, TagLens sends your question and the fact sheet described above to the endpoint you chose — Google AI Studio, or another OpenAI-compatible endpoint you name — and shows you the answer. That request carries your key and nothing about you or your browser beyond the fact sheet. What the provider does with what it receives is governed by that provider's terms; on Google's free tier, for example, Google states that content may be used to improve its products, and TagLens says so on the screen where you connect. No question is sent until you ask one. When a question needs a row the fact sheet does not carry, the model may ask TagLens for rows by event name and time window; TagLens answers with at most twenty rows per request, a few requests per question, each row scrubbed by the same rules as the fact sheet, and the answer's footer names every lookup it made.

The third is the optional Jev classification request described under Page checks above. Selected, previewed page text goes to TypeSafe only when you approve it and press classify; it never runs automatically in the background.

The fourth is the optional Preview image request described above. It fetches only an image address already captured in the recording, after you request it.

The ask ChatGPT button on the header (the same press as for ChatGPT in the export menu) saves the raw export on your device — every recorded event with its full payload, values as recorded, the same file as the json export — and opens chatgpt.com with TagLens's reading instructions typed into the message box; you attach the file there yourself. It exists so you can ask about your own recording without connecting a key. TagLens sends nothing; the file leaves your device only when you upload it, under that service's terms.

There is no other fetch, no XMLHttpRequest, no sendBeacon and no WebSocket anywhere in the extension.

What TagLens never does

  • It never automatically uploads your recordings or browsing history. Page checks sends selected, previewed text to TypeSafe only on your explicit classification request. The AI analysis feature sends a fact sheet of names, counts and values, and rows the model asks for under the same rules — never a whole recording, never a raw payload, never an identifier — and only to an endpoint you chose, with a key you supplied, when you ask a question.
  • Limited Use. TagLens's use of information received from Google APIs, and of any data it handles, adheres to the Chrome Web Store User Data Policy, including the Limited Use requirements. It transfers that data nowhere, uses it for no purpose other than showing you the diagnosis you asked for, sells it to nobody, and no human at TagLens ever reads it, because it never reaches TagLens: it stays on your machine except for the explicit AI analysis and Jev classification requests described above, which go to your chosen provider.
  • It never sells or shares data, because it never receives any.
  • It never blocks, redirects, or modifies the requests it observes — it only reads them.
  • It contains no eval, no new Function, and no remotely-loaded code. All code that runs is the code reviewed and shipped in the package.

The debugger permission

The debugger permission is granted when you install TagLens, and Chrome shows it to you at that moment. It cannot be made optional: Chrome refuses to accept debugger in an extension's optional_permissions and silently drops it, which is why an earlier version of TagLens that tried to ask for it only on demand had a replay button that could never work.

It is used for one thing: re-driving a recorded journey when you press replay. TagLens opens a new window of its own for the replay and attaches the debugger only to the tab inside it, for the length of that run, detaching when the run ends or is stopped. It is never attached to a tab you are browsing in, and never while you are recording by hand or reading a recording back. A replay is itself recorded, in the separate window, so for the length of a replay TagLens is both recording and attached — to the window it opened, never to yours.

While the debugger is attached, Chrome displays its own banner across the top of the tab saying TagLens is debugging it. If you would rather not grant it, the only way to decline is not to install the extension — but nothing is sent anywhere either way; see “What TagLens never does” above.
